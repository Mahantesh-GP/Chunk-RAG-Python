# Spec Kit — Brownfield Q&A
### Answers for Satish's Architecture Review Questions

---

## Q1: How will you add a new feature — how does it propagate changes to existing code, and how does it update requirements/specs?

**Propagation to existing code:** Spec Kit does not automatically detect impact on existing code. The Copilot agent *can* discover existing implementation from the repository, but only when explicitly instructed to look. For anything touching multiple existing files, this must be stated directly at `/plan` time:

```
/plan
Scan all controllers, middleware, frontend API consumers, and tests in the
current codebase. Identify every location that needs to change to adopt
[the new pattern/feature]. Generate repository-wide tasks covering all of them.
```

Without this explicit instruction, the agent scopes itself to the current feature only.

**Updating requirements/specs:** depends on which of three persistence models applies:

- **Flow-Forward** — genuinely new capability → a new `specs/00X-feature-name/` folder is created. Previous specs stay untouched as historical record.
- **Living Spec** — a requirement changes *existing, already-specified* behavior → edit that feature's existing `spec.md` in place, then regenerate `plan.md`/`tasks.md` to match, and re-validate with `/analyze`.
- **Flow-Back** — an insight is discovered *mid-work* (during `/plan`, `/tasks`, or `/implement`) that should reshape an earlier artifact → capture it wherever it was found, then propagate the change backward into whichever artifacts now disagree, and run `/analyze` before continuing.

**Decision test:** new capability → Flow-Forward. Changing existing behavior, known before starting → Living Spec. Only realized while doing the work → Flow-Back.

## Q2: How are bugs going to be addressed?

First classify *where* the gap actually is — this determines the fix, not just the symptom:

- **Spec-to-implementation gap** — the spec was correct, but the generated code diverged from it anyway. Fix: correct the code, then validate with `/converge` to confirm it now matches spec/plan/tasks.
- **Intent-to-spec gap** — the spec itself missed the case, because the original requirements conversation missed it. Fix: correct the *spec first* (Living Spec model), regenerate downstream plan/tasks, then re-implement. Fixing only the code without updating the spec means the same bug class can recur the next time that code is regenerated by AI, since the spec never captured the correction.

**Discipline point:** even small, seemingly trivial fixes should ideally update the spec, not just the code — a direct code-only patch risks being silently overwritten the next time that code is regenerated, because AI generation is non-deterministic and the spec is what the regeneration is based on.

## Q3: How can an architectural change affect the system?

Two distinct scenarios:

**1. A deliberate, standing rule change** (e.g., adopting a `Result<T>` response pattern across all APIs):
- Update `constitution.md` first, since it's the one artifact every downstream command reads.
- Explicitly ask `/plan` to scan the whole repository for impact and generate repository-wide remediation tasks (see Q1's prompt pattern) — propagation to *old*, already-implemented code does not happen automatically; it must be requested.

**2. An unplanned change made outside the process** (e.g., a hotfix under deadline pressure):
- This is architectural drift. Recovery:
  1. Audit: *"Compare the current codebase structure against plan.md and data-model.md. List every place they disagree."*
  2. Update `constitution.md` if the change is now the permanent standard.
  3. Regenerate `plan.md`/`data-model.md` from the real code — don't hand-edit from memory.
  4. Update `tasks.md` honestly — mark divergent tasks "implemented differently," don't blanket-mark them complete.
  5. Log *why* the drift happened, so the next person understands it wasn't an oversight.

**Honest caveat:** constitution rules are strong guidance, not compiler-enforced constraints. This was verified experimentally — a constitution rule stated as "MUST" (Clean Architecture layering) was still violated in generated code (a flat `Data/Models/Services` structure instead of `Domain/Application/Infrastructure/API`). Mitigation: write rules with zero interpretive gap (e.g., "no business logic in controllers, including simple CRUD operations, with zero exceptions"), and verify compliance directly with `/converge` rather than assuming it.

## Q4: Modernization — reuse the existing application's functionality, but rebuild it using new architecture/approach

This is the "keep the behavior, replace the implementation" scenario — relevant directly to real migration projects (e.g., a Claims application rewrite).

```
Old system
   ↓
Project discovery / ProjectContext.md
   (discover WHAT the old system does, and its current implementation,
    constraints, and non-negotiables — e.g., "stored procedures cannot
    be modified")
   ↓
Reverse-engineer spec.md from the old system's BEHAVIOR, not its
implementation — for the SPECIFIC module/change being worked on now,
NOT the whole legacy system in one pass (see caveat below)
   ("spec.md describes what the system must do; it deliberately excludes
     how the old system happened to do it")
   ↓
Write a NEW constitution.md — for the TARGET architecture,
   not the legacy one
   ↓
/plan against the new stack, using that module's spec.md +
   the new constitution.md as inputs
   ↓
/tasks → /implement incrementally (module by module; each module can
   be its own Flow-Forward spec)
   ↓
Validate PARITY — quickstart.md acceptance criteria are derived from
   the OLD system's actual behavior, proving no functionality was lost
   in the rebuild
```

**⚠️ Important caveat — reverse-engineering is a derivative artifact, and this has been demonstrated to cause real problems, not just a theoretical risk:**

A reverse-engineered spec is one step removed from the real source of truth (the actual old code). Each further derivation risks silently losing information — because if the codebase was fully understood already, it wouldn't be brownfield in the first place.

**This was tested directly** (Hari Krishnan, "Spec-Driven Development on Brownfield Projects"): a change proposal built from a previously reverse-engineered, whole-system spec missed a real database check-constraint issue — existing data needed a migration step before a schema change could be safely made. A second attempt, built by going straight to the real code fresh for just that one change (skipping the old reverse-engineered spec entirely), caught the issue the first approach missed.

**The corrected recommendation:**
- ✅ Reverse-engineer a spec for **one specific module or change at a time**, always going directly to the real code as the source of truth for that change.
- ❌ Do **not** reverse-engineer one comprehensive spec for the whole legacy system upfront, and then treat it as a trustworthy foundation for later, unrelated changes — each additional change built on top of a derived spec compounds the risk of missing something the original code actually encodes (like our DB constraint example above).
- Over time, expect the modernized system to be a natural patchwork — areas you've actively rebuilt have real, verified specs; untouched legacy areas may have none yet, and that's fine, especially for stable or rarely-changed code.

**The key mechanism that makes this possible:** `spec.md`'s deliberate "no implementation details" rule. A spec reverse-engineered from the old system captures pure business behavior, so it can be re-planned against a completely different architecture without dragging legacy technical decisions along. The old implementation is used for *discovery only* — it must not leak into the spec itself.

**Real constraints from the old system** (e.g., "stored procedures cannot be modified") belong in `ProjectContext.md`'s Constraints section, and should also be reflected in the new `constitution.md`, so every generated plan respects them automatically rather than needing to be repeated in every prompt.

**Reverse-engineering prompt example:**
```
/specify
This feature already exists in the old codebase (see #OldControllerName.cs
and #ProjectContext.md). Reverse-engineer a spec.md that documents its
current actual behavior — functional requirements, edge cases, and
acceptance criteria — based on what the code does today, not how it's
implemented. Exclude all implementation detail.
```
